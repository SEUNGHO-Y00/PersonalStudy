# Cisco Switch Crypto Issue

The difference comes down to how the key pair was named and generated inside the switch’s operating system.

When you look at the IOS Keys in SECSH format, the name you see directly above the Base64 key string tells you what triggered its creation:

1. hostname.domain-name (User-Generated SSH Key)

This is the standard, manual key name created when you explicitly configure the switch for SSH.

• How it gets there: You configured a hostname (e.g., SwitchA), a domain name (e.g., ip domain-name corp.local), and manually executed crypto key generate rsa. The switch names the key pair by merging them together: SwitchA.corp.local.

• What it means: This is the intentional identity you gave the switch. It is cleanly tied to your company's naming architecture.

2. TP-self-signed-XXXXXXXXXX (System Auto-Generated Key)

This is a standard Public Key Infrastructure (PKI) key pair that Cisco IOS generates automatically.

• How it gets there: The moment someone enables the Web GUI on the switch using the command ip http secure-server (HTTPS), the switch realizes it needs an SSL certificate. If you haven't manually created a key pair yet, Cisco automatically provisions a local "Trustpoint" (TP) and generates a self-signed certificate, naming the cryptographic key TP-self-signed plus a random string of numbers (usually based on the device's serial number). 

• What it means: Because a key pair now exists in the system memory, Cisco's SSH server grabs it and uses it as the default host key if no other manual key is found. 

Comparison Overview

| Feature |	hostname.domain-name |	TP-self-signed |
|---|---|---|
| Origin |	Manually configured by an administrator. |	Auto-generated by the switch for HTTPS/WebUI services. |
| Purpose |	Specifically intended for SSH remote access. |	Intended for the HTTPS Web GUI, but shared with SSH. |
| Key Size Control |	You choose exactly how secure it is (e.g., 2048 bits). |	The switch assigns a default size (which on older IOS versions might only be a weak 1024 bits). |
| Best Practice |	Highly Recommended for production networks. |	Primarily used as an out-of-the-box fallback mechanism. |

Which one should you use?

You should always prefer the manual domain-name key. Leaving your switch running on the automated TP-self-signed key is fine for temporary lab environments, but in production, modern SSH clients may reject it if the auto-generated bit length is too weak (below 2048 bits).

If your switch is using the TP-self-signed key for SSH and you want to clean it up, you can manually build your preferred key via crypto key generate rsa modulus 2048. Once built, you can configure SSH to ignore the TP-self-signed key and strictly use your new label.

---

If SSH works when the switch uses the TP-self-signed key but fails when using your manually created domain-name key, the switch is overriding your manual key. 

This happens because Cisco's HTTPS/Web UI engine (ip http secure-server) frequently defaults to binding the SSH server to the auto-generated certificate trustpoint. When you generate a manual domain key, the switch keeps using TP-self-signed for incoming SSH traffic, completely ignoring your new key.

How to Force the Switch to Use Your Domain Key

To break the TP-self-signed hold and explicitly force the switch to use your corporate domain-name key, apply the following configuration:

1. Find the Exact Name of Your Domain Key
First, view your keys to find the exact label assigned to your manual key pair (it usually looks like hostname.domain-name):

```text
switch# show crypto key mypubkey rsa
```

2. Explicitly Bind SSH to That Key Label

Go into global configuration mode and use the ip ssh rsa keypair-name command. This overrides any auto-generated system defaults and forces the SSH daemon to route strictly through your specific key:
```text
switch# configure terminal
switch(config)# ip ssh rsa keypair-name YourSwitchName.yourdomain.local
```
(Replace YourSwitchName.yourdomain.local with the exact string you found in step 1).

3. Refresh SSH Version 2

Re-apply the version enforcement to make sure the server restarts its handshake protocol using the correct key:
```text
switch(config)# ip ssh version 2
```

If it Still Fails: The "Clean Slate" Method

If the switch refuses to flip over, the TP-self-signed certificate might be locked into the HTTPS service. You can safely clear and rebuild it using a labeled RSA key so both HTTPS and SSH share the clean configuration: 

```text
switch# configure terminal
```

1. Temporarily turn off the secure web server

```text
switch(config)# no ip http secure-server
```

2. Clear out all existing RSA keys

```text
switch(config)# crypto key zeroize rsa
```

3. Generate a brand new, cleanly labeled 2048-bit key

```text
switch(config)# crypto key generate rsa general-keys label SSH-KEY modulus 2048
```

4. Force SSH to use this labeled key

```text
switch(config)# ip ssh rsa keypair-name SSH-KEY
switch(config)# ip ssh version 2
```

! 5. Turn HTTPS back on (it will now hook into your new clean key)

```text
switch(config)# ip http secure-server
switch(config)# end
switch# write memory
```
